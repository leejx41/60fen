# 「60分」执行力 App — 技术栈锁定 v1.0

> **本文档一旦确认，第一版开发期间不再讨论技术选型。**
> 想改之前，先看第 6 节的变更规则。

---

## 0. 选型第一原则

**按「未来由你接手维护」的标准选，不按「写起来最快」的标准选。**

代码最终是长期维护者的资产。所以优先顺序是：

1. **生态规模** —— 半年后遇到问题，能不能搜到答案
2. **可读性** —— 一个月后回来，还看不看得懂
3. **迁移可能性** —— 想加后端 / 想上架时，要不要重写
4. 最后才是"写起来快不快"

> 这条原则解释了很多"看起来多余"的选择。比如为什么不用最简单的 `localStorage`、为什么不用最省事的 `Tailwind`——它们的短期优势换不来长期可维护性。

## 2. 逐项理由

### 2.1 React（不选 Vue）

| 维度 | 说明 |
|---|---|
| **生态规模** | 最大。长期项目最大的风险是"遇到怪问题搜不到答案"，React 把这个问题降到最低 |
| **跨端退路** | 将来要做 App，Capacitor / Expo 都能直接包住 React 代码；要做小程序，Taro 用 React 语法 |
| **招聘/求助** | 如果哪天需要别人帮忙看代码，React 是最通用的沟通语言 |

**不选 Vue 的理由**：Vue 在国内生态同样成熟，uni-app 做小程序更主流。但 React 在"跨端 + 通用性"上更稳。这不是说 Vue 不好，而是**长期项目选生态最大的那个，容错率最高**。

### 2.2 TypeScript（不选 JavaScript）

这个项目的类型收益比一般项目更明显，因为**数据关系绕**：

- `branch`（处理路径）和 `reasonKey`（理由归属）是两个概念，绝不能混
- 证词指纹要区分 `tag:A` 和归一化原话
- 状态机有 10 个界面、5 种计划状态

这些地方一旦字段写错，**在 JavaScript 里要等到运行时、甚至等到用户用了两周之后才会发现**。而在 TypeScript 里，编辑器当场就红。

**更关键的一点**：这个产品不做后端，数据全存在用户设备上。一旦数据结构写错需要改，就要给已有的用户数据写迁移脚本——**类型能在写错的那一刻就拦住你**。

`strict: true` 必须开，不开等于没写 TS。

### 2.3 Vite（不选 Next.js）

**不选 Next.js 的理由**：
- 它是服务端渲染框架，而本产品是纯客户端应用，不需要 SSR
- 它会引入"服务端 / 客户端组件""数据获取"等一整套概念，**对纯本地应用是纯负担**
- 部署会变复杂（虽然 Vercel 上很简单，但国内访问是问题）

Vite 是当前纯前端项目的标准构建工具，配置少、启动快、生态成熟。

### 2.4 CSS Modules + CSS 变量（不选 Tailwind）

**不选 Tailwind 的理由**：
- 它是一套需要学习记忆的类名体系，长期维护时"`p-4 text-sm` 到底长什么样"会变成负担
- 本产品只有 10 个界面、视觉极简，**用不上 Tailwind 的效率优势**

**选 CSS Modules 的理由**：
- Vite 原生支持（`.module.css`），**零配置**
- 解决了裸 CSS 的类名冲突问题（长期项目必然会遇到）
- 写的就是标准 CSS，任何资料都能直接用

CSS 变量负责主题色、间距、字号，`global.css` 里集中定义。

### 2.5 zustand（不选 Redux）

- 4KB，API 只有几个函数，一天能学完
- 不用写 action / reducer / dispatch 那套样板代码
- 长期项目不需要 Redux 那套"强约束"——**本项目状态量很小**

**不用 React Context 的理由**：Context 在状态频繁更新时会导致整棵子树重渲染，而这个产品列表会频繁变化。

### 2.6 IndexedDB + idb（不选 localStorage）

**不选 localStorage 的理由**：

| 问题 | 后果 |
|---|---|
| 同步阻塞 | 每次读写卡住主线程，列表多了会明显卡 |
| 5MB 上限 | 长期使用会撞墙 |
| 只能存字符串 | 每次都要 `JSON.stringify` / `parse`，性能差且容易出错 |

IndexedDB 是浏览器里**为结构化数据设计的存储**，异步、容量大。原生 API 太啰嗦，`idb` 这个库只有 2KB，把它包成 Promise 风格。

**这一项还对应一个专业知识点**：浏览器存储机制（Cookie / localStorage / IndexedDB / Cache Storage 的差异），是这个项目里最值得学的一块。

### 2.7 不用路由库

**理由**：这个产品的界面是**流程性**的（阻断式拦截卡），不能随便跳转。

用 React Router 会带来一个隐蔽问题：**用户可以刷新、或者直接访问 URL，跳进"拦截卡"这种中间状态**，而那时数据可能还没准备好。为了避免这个坑，要么写一堆守卫，要么就干脆不用路由。

**替代方案**：一个 `view` 状态机 + 把当前 view 写进 URL hash。

```ts
type View = 'home' | 'add' | 'addWish' | 'intercept' | 'branchA'
          | 'branchB' | 'branchC' | 'branchD' | 'acted'
          | 'fullScore' | 'nightCheck' | 'settings';
```

刷新时读 hash 恢复，非法状态直接回 `home`。**20 行代码，比引入一个路由库更好控制。**

### 2.8 Vitest

与 Vite 同源，零配置。第一版只测三个纯函数模块：

- `logic/reason.ts`（理由归一化）
- `logic/intercept.ts`（补拦截）
- `logic/testimony.ts`（证词计算）

这三个是最容易写错、且错了最难发现的地方（错了不会报错，只会让数据悄悄变错）。

### 2.9 部署 Cloudflare Pages

免费额度高，自动部署，国内基本可访问。

## 3. 明确不用的东西（防摇摆清单）

**这份清单比"选了什么"更重要。** 下次你想加这些东西时，先回来读一遍。

| 不用 | 为什么不用 |
|---|---|
| **Next.js / Nuxt** | 纯客户端应用，不需要 SSR，引入的服务端概念全是负担 |
| **Redux / MobX** | 状态量太小，样板代码成本大于收益 |
| **Tailwind CSS** | 需要学一套类名体系，10 个界面用不上它的效率优势 |
| **Ant Design / Element Plus / MUI** | 本产品视觉极简且高度定制，UI 库的既有样式反而是负担 |
| **dayjs / moment / date-fns** | 所有时间都是 `HH:MM` 字符串或 `YYYY-MM-DD`，原生 `Date` 足够，少一个依赖少一个坑 |
| **React Router** | 流程性界面不该允许自由跳转，见 2.7 |
| **Firebase** | 国内访问不稳定；未来上后端优先考虑 Supabase |
| **自建后端（Node/Java/Python）** | 4 个用户不需要，运维成本远超收益 |
| **React Native / Expo** | 第一版做网页，跨端是第三版的事 |
| **CSS-in-JS（styled-components / emotion）** | 运行时开销 + 需要额外 babel 配置，CSS Modules 已经够用 |
| **任何 UI 组件库的"主题系统"** | 会被它的设计语言绑架，改起来比重写还慢 |

## 4. 版本锁定

```json
{
  "engines": { "node": ">=20" },
  "dependencies": {
    "react": "18.3.x",
    "react-dom": "18.3.x",
    "zustand": "4.5.x",
    "idb": "8.0.x"
  },
  "devDependencies": {
    "vite": "5.4.x",
    "typescript": "5.5.x",
    "@vitejs/plugin-react": "4.3.x",
    "vitest": "2.x"
  }
}
```

**锁定规则**：
- 全部用 `x` 结尾的小版本范围，不锁死补丁版本（自动拿安全更新）
- **不追新大版本**：React 19、Vite 6 出来后，等生态稳定再升
- 升级前先建一个分支跑通全流程再合并

## 5. 长期路线：什么时候加什么

你说要长期做下去，所以这条路线要提前看清楚——**每一步都是被真实信号触发的，不是按计划表加的**。

### 第一版（现在）→ 本地存储 + 静态部署

触发信号：无。现在就开始。

### 第二版 → 接 Supabase（后端）

**触发信号（出现任一才做）**：
- 试用者说"换了手机数据没了"且仍愿意继续用
- 你想看真实的聚合指标（理由填写率、拆解转化率）
- 用户超过 10 个

**改动范围**：只改 `app/src/db/repo.ts` 一个文件 + 加一层认证。业务代码零改动。

**这就是为什么现在就要把 repo.ts 单独抽出来。** 而且它的接口**从第一天就设计成 async**，即使本地实现很快，也按"未来是网络请求"的方式写。

### 第三版 → PWA 离线 + 可安装

**触发信号**：用户反馈"想从主屏幕直接打开"或"希望离线也能用"。

**改动范围**：加 `manifest.webmanifest` + Service Worker。

> ⚠️ **Service Worker 有个经典坑**：它会缓存旧版本，导致用户永远看到老界面。加之前要先设计好版本更新策略。

### 第四版（可选）→ 原生 App

**触发信号**：有真实用户长期使用，且推送是明显瓶颈。

**方案**：Capacitor 包壳（复用现有 React 代码），或换 Expo。**不要现在考虑。**

## 6. 变更规则

技术栈不是不能改，但**不能因为"用起来不爽"就改**。

**允许改的唯一条件**：遇到**完全做不下去**的阻塞。

区分两者：

| 情形 | 允许改吗 |
|---|---|
| "zustand 的 API 我不习惯" | ❌ 不爽，不改 |
| "Tailwind 写样式好像更快" | ❌ 不爽，不改 |
| "TypeScript 报错太烦了" | ❌ 不爽，不改 |
| "IndexedDB 在某些机型上完全不可用" | ✅ 阻塞，评估替代 |
| "Vite 5 与某个必须用的库不兼容" | ✅ 阻塞，评估降级 |

**改之前的固定动作**：

1. 写一页说明：改什么 / 为什么非改不可 / 影响多少文件 / 回退方案
2. 一次只改一项，改完跑通全流程再动下一项
3. 建独立分支，不在主分支上试

## 7. 这套栈三年后还能用吗

| 技术 | 三年后风险 | 判断依据 |
|---|---|---|
| React | 极低 | 十年了仍是主流，生态最厚 |
| TypeScript | 极低 | 已是事实标准 |
| Vite | 低 | 已取代 webpack 成为默认选择 |
| CSS Modules | 极低 | 是 CSS 规范的一部分，不会消失 |
| zustand | 中低 | 轻量库可能被替代，但只有 4KB，换起来成本极低 |
| IndexedDB | 极低 | 浏览器标准 API |
| Cloudflare Pages | 中 | 平台可能调整策略，但静态托管方案可随时平移到任何地方 |

**结论**：这套栈里**没有一个是"潮流型"技术**，全部是已经稳定多年的基础设施。三年后你回来，仍然能看懂、能改、能找到资料。

---

## 8. 一句话总结

> **React + TypeScript + Vite + CSS Modules + zustand + IndexedDB，部署 Cloudflare Pages。**
> **不引入路由库、不引入 UI 库、不引入 Tailwind、不做后端。**

这句话就是锁定的内容。第一版开发期间，不再讨论。
