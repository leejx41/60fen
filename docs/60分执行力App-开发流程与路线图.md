# 「60分」执行力 App — 开发流程与四周路线图

> 面向：计算机专业大三学生，个人项目，目标 = 做出来 + 学到东西
> 前置文档：PRD v1.2、交互原型

---

## 0. 先回答那个问题

**PRD 定完不等于进入开发，中间还差一步：技术方案。**

跳过这一步，常见结局是：写到第三周发现数据结构装不下需求，开始重构，重构到一半放弃。个人项目半途而废，多数死在这里而不是死在不会写代码。

而这一步恰恰是学习价值最高的地方——**建模能力、技术权衡**，这两样是校招面试里最难伪装的东西。

## 2. 第 3 步：技术方案要做什么

### 2.1 数据模型（先画图，再写代码）

这个产品只有四张表，先写在纸上确认字段，再动手：

**`plan`（计划）**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT/UUID | 主键 |
| title | TEXT | 一句话，≤20 字 |
| scheduled_at | DATETIME | 计划时间（必填） |
| downgrade_action | TEXT | 最没阻力的一步，可空 |
| status | ENUM | `pool` 想做池 / `today` 今日池 / `done` / `deferred` 搁置 / `passed` 放行 |
| created_at | DATETIME | — |

**`intercept`（拦截记录）**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT | 主键 |
| plan_id | TEXT | 外键 → plan.id |
| reason_text | TEXT | 用户原话，可空 |
| reason_type | ENUM | `tag` 点了标签 / `free` 自己写 / `null` 未填 |
| reason_key | TEXT | **证词指纹**：标签用 `tag:A`，自由理由用归一化原话 |
| branch | ENUM | `A` / `B` / `C` / `D` / `went` |
| shown_at | DATETIME | 卡片展示时间 |
| resolved_at | DATETIME | 用户做出选择的时间，可空（未响应） |
| action_taken | BOOLEAN | 是否最终行动 |

**`testimony`（事后证词）**
| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT | 主键 |
| intercept_id | TEXT | 外键 → intercept.id |
| answer | ENUM | `regret` 有点后悔 / `glad` 庆幸没去 / `forgot` 想不起来了 |
| created_at | DATETIME | — |

**`settings`（设置）**
| 字段 | 类型 | 说明 |
|---|---|---|
| ref_capacity | INTEGER | 参考容量，默认 3 |
| testimony_enabled | BOOLEAN | 默认 true |

**三张关系**：`plan 1 — n intercept 1 — 0..1 testimony`

> **建模要点 1**：`intercept` 单独成表是必须的，因为"一次计划可能被拦截多次"（改期后重新到点）。如果把它塞进 `plan`，后面加证词会很难受——这就是典型的"数据结构装不下需求"。

> **建模要点 2（重要，容易做错）**：`branch` 和 `reason_key` 必须分开。
> - `branch` 记录**走了哪条处理路径**（写自由理由的人，路径也是 A，因为要进拆解页）
> - `reason_key` 记录**这条理由归谁**（写自由理由的人，归属是他自己的原话，不是标签 A）
>
> 如果为了省事把 `reason_key` 直接填成 `branch`，系统就会给一个写"1111111"的用户展示"我怕今天做不好"的历史统计——**编造归类，和编造原话是同一类错误**。
>
> 证词指纹的归一化规则（MVP）：去除首尾与中间多余空格、中英文标点统一、转小写。**不做语义相似度**。

### 2.2 技术选型（选能一周跑起来的）

| 层 | 推荐 | 理由 |
|---|---|---|
| 前端 | React / Vue 任选熟悉的 | 你已经会哪个就用哪个，别为了项目学新框架 |
| 状态管理 | 项目小，`useState` + 一个 store 就够 | 别上 Redux，过度设计 |
| 存储 | IndexedDB（量大）/ localStorage（量小） | 单机版无需后端，省掉一大块 |
| 时间处理 | `dayjs` | 比 `Date` 好用，4KB |
| 构建 | Vite | 快，配置少 |
| 部署 | GitHub Pages / Netlify / Vercel | 免费，`git push` 即上线 |

**关键决策：第一版不做后端。** 所有数据存本地。这样你少写登录、少写接口、少租服务器，把时间全花在核心链路上。等真有第二个用户了再说。

### 2.3 部署方案

- 有域名更好，没有也行
- **务必先跑通一次自动部署**：`git push` → 自动构建 → 线上可访问。这件事在第 4 阶段做，不要留到最后——最后做的话，你会卡在各种环境问题上，而那时你已经很累了

## 3. 必须早解决的技术约束：推送

### 3.1 问题

产品的核心动作是「到点推送拦截卡」。但：

- **网页 / PWA**：手机浏览器在后台会被系统回收，定时器不可靠；iOS 对 Web Push 限制严格。**无法保证准点推送**
- **微信小程序**：订阅消息需要用户每次主动授权（一次订阅对应一条），不能静默定时推送
- **原生 App**：本地通知可靠（Android 用 `WorkManager`/`AlarmManager`，iOS 用 `UNUserNotificationCenter`），但要写两端

### 3.2 解法：把触发拆成两条路

```
到点 ──► 尽力推送（有通知权限就发）
          │
打开应用 ──► 检查是否有「已到期且未响应」的计划
          └─► 有，立刻弹拦截卡（补拦截）
```

**这个改动为什么成立**：人早上第一件事就是拿手机，**主动打开应用的概率远高于点开系统通知**。补拦截不仅绕开了技术限制，甚至可能比推送更有效。

### 3.3 需要回改 PRD 的地方

把 E1「当到达用户设定的计划时间时，系统应推送拦截卡」改为：

> E1. 当到达用户设定的计划时间且具备通知能力时，系统应推送拦截卡。
> E1a. 当用户打开应用且存在「已到期未响应」的计划时，系统应立即展示该计划的拦截卡。

**这一课值得记住：技术约束反过来改需求，不是妥协，是产品设计的常态。** 想清楚哪条是核心价值（拦住放弃那一刻）、哪条只是实现手段（用推送还是用补拦截），改的永远是手段。

## 4. 开发方式：垂直切片，不要水平切片

| 错误（水平） | 正确（垂直） |
|---|---|
| 先做完所有页面 | 先建一件事 + 到点拦截 + 点"我去了" |
| 再写完所有逻辑 | 跑通这一条，真的能用 |
| 最后连起来调 | 再加分支 B/C/D |
| → 第 7 周才发现装不下 | → 第 1 天就有能用的东西 |

**判断标准**：任何一周结束时，你手上应该有一个**能真实使用**的东西，而不是"还差一点就能用"的零件集合。

## 5. 四周路线图

### 第 1 周：技术方案 + 工程搭建

| 任务 | 产出 | 学到什么 |
|---|---|---|
| 画数据模型，写建表语句 | ER 图 + schema 文件 | 建模、关系设计 |
| 定技术选型，写一页方案说明 | 技术方案.md | 技术权衡、做取舍 |
| 建 Git 仓库，配 ESLint/Prettier | 仓库可提交 | 工程规范 |
| 部署一个"Hello World"到线上 | 线上 URL | CI/CD 全流程 |

> 第 1 周不写任何业务代码。听起来浪费，实际是整条路线里性价比最高的一周。

### 第 2 周：最窄的垂直切片

只做三步：**建计划 → 到点/打开时拦截 → 点"我去了"**

- 能创建、能存储、能弹出、能记录
- 自己用一天

### 第 3 周：四个分支 + 当晚一问

- 分支 A（校准句 + 降档动作）、B、C、D
- 事后证词采集 + 第 3 次举证

### 第 4 周：测试 + 收尾 + 复盘

- 给核心逻辑写单测（重点：日期边界、理由指纹计数、超载提示每日一次）
- 按 PRD 第 10 章验收清单逐条自查（尤其 10.2 价值观红线）
- 找 3 个人试用，记录他们第一个卡住的地方
- 写一篇复盘：哪条 PRD 假设被证明是错的

## 6. 学习地图：每一步对应什么课

| 阶段 | 对应课程/知识 |
|---|---|
| 数据模型 | 数据库原理（范式、索引、外键） |
| 技术选型 | 软件工程（架构权衡、非功能需求） |
| Git 与部署 | 软件工程 / 操作系统（进程、环境变量） |
| 拦截定时逻辑 | 操作系统（定时器、事件循环）、计算机网络（HTTP 缓存） |
| 数据存储 | 数据库原理（事务、持久化）、浏览器存储机制 |
| 测试 | 软件测试（等价类、边界值） |
| 埋点与指标 | 数据分析基础 |

> 顺带说一句：你正在备考 408，这个项目里的**操作系统（定时器、进程调度）**和**计算机网络（HTTP、缓存）**会直接反哺你的专业课理解。做项目不是为了挤占复习时间，很多时候它能让你把概念真的搞懂。

## 7. 五个常见的坑

1. **想先学完框架再动手** → 永远学不完。用你会的，先把东西跑起来
2. **过早引入后端和登录** → 单机版能验证的事，不要用两周去搭服务
3. **追求完美 UI** → 这款产品的价值 90% 在文案和流程，不在视觉
4. **不留可回退的提交** → 每天至少一次 `commit`，每次 commit 只做一件事
5. **上线后才第一次部署** → 环境问题会集中爆发在你最累的时候

## 8. 下一步该做的三件事（按顺序）

1. 画数据模型（纸上 20 分钟）
2. 写一页技术方案（含推送的处理方式），自己讲一遍
3. 建仓库 + 部署 Hello World 上线

做完这三件，你才算真正进入开发。
