## 1. 背景与问题

### 1.1 现象

大量计划不是「做砸了」，而是**从来没有开始**。用户在行动前一刻，会产生一个看似合理的判断——"我太累了，练了效果不好"、"方案还没想周全，先放一放"——然后合法地放弃。

### 1.2 根因：不是懒，是被自己说服了

这句话在用户自己听来**是一个事实判断**，不是一个借口。所以他不需要鼓励，他需要**有人检验他的论证**。

完美主义的论证结构只有一个漏洞：它建立在一个**不存在的选项**上——"要么做到最好，要么不做"。真实世界里的第三个选项（今天能做到的那个版本）被他自己划掉了。

### 1.3 现有工具为什么无效

待办清单、打卡、番茄钟、习惯养成，都在**加动力**。但被说服的人不缺动力，缺的是**反驳**。所以这些工具在"用户已经想放弃"的那一刻全部失效。

### 1.4 产品机会

> 做一个只在"放弃那一刻"出现的工具。
> 它不安慰、不催促、不打气，只做一件事：**把你的论证拆开给你看。**

### 1.5 产品原则（四条不可违背）

所有取舍以这四条为准。**任何需求与它们冲突时，需求让步。**

**① 60 分主义不是反卓越。**
追求完美不是病，「因为追求完美所以不开始」才是病。产品绝不能让用户觉得"它在阻止我变好"。

**② 绝不施压。**
任何带催促、审判、代价的设计都会催生"必须完成"的完美心理，与理念直接冲突。宁可少管，不可多管。

**③ 可数资源，不可数质量。**
不出现任何针对完成质量的分数、评级、完成度百分比。

**④ 60 分是底线，不是目标。**（v1.6 新增）
60 分的作用是让人敢于开始，**不是给人一个"做到这就够了"的天花板**。做到 100 分同样值得真诚的肯定，而且这种肯定不能打折——**禁止任何"你本来可以只做 60 分"式的降格表达**。

> 注：这条原则的由来是一次真实的文案错误。原满分反馈写作「100 分。你本来可以只交 60 分的。」——本意是肯定超额付出，实际听感是把 60 分设成了参照系，等于给成就打折。**理念是写给做产品的人看的判断，不是对用户说的话。** 把前者直接搬进界面，就会从"帮你开始"变成"你这样就够了"。

## 2. 目标与非目标

### 2.1 试用版要验证的三件事

| # | 验证问题 | 判定方式 |
|---|---|---|
| V1 | 用户是否愿意在拦截时如实填写理由？ | 「理由填写率」≥ 40% |
| V2 | 「被推翻的借口数」是否大于 0？ | 7 天内 ≥ 1 次 |
| V3 | 校准句是否产生"啊对"的效果？ | 拆解页 → 行动的转化率 ≥ 30% |

### 2.2 非目标（本版明确不做）

- ❌ **不做任何质量评分、完成度、评级、排行榜**（原则性排除，永久不做）
- ❌ 不做社交、好友、见证人、分享
- ❌ 不做 AI 生成、语音识别、语义分析
- ❌ 不做账号体系、云同步、多设备
- ❌ 不做完整任务管理（子任务、标签、看板、日历视图）
- ❌ 不做习惯养成体系、连续天数、勋章
- ❌ 不做数据统计报表（除试用期必需的三项）

> **范围纪律**：以上任何一项进入需求，都会把试用周期从 7 天拖成 7 周。试用版的唯一目的是验证 V1–V3。

## 3. 目标用户与场景

### 3.1 首批用户

**产品作者本人 + 3–5 位同类用户**（自称"想得多做得少"、"总在准备阶段"的人）。
不做用户分层，不做用户画像细化——试用期样本太小，细分没有意义。

### 3.2 典型场景

| 场景 | 用户状态 | 产品介入点 |
|---|---|---|
| 早上 7:00 计划健身，昨夜被噪音吵醒 | 半睡半醒，正在找一个不去的理由 | 到点推送拦截卡，把理由接住 |
| 晚上计划写方案，反复觉得没想清楚 | 焦虑，开着文档不写字 | 拦截卡 + 校准句 |
| 计划已过期三天没动 | 回避，不敢看列表 | 不做任何催促，静默回想做池 |

## 4. 用户故事

- 作为一个反复拖延的人，我希望**在我想放弃的那一刻被问一句"你大概会用什么理由不去"**，以便把心里的借口说出来，而不是直接关掉。
- 作为一个人，我希望**能用我自己的话描述理由，而不是从别人预设的选项里挑**，以便这个工具不显得在替我说话。
- 作为一个被自己说服的人，我希望**看到"我实际在比较哪两个选项"**，以便发现我一直在拿"最好"和"不做"比。
- 作为一个真的有事的人，我希望**搁置一件事时不被审判、不被计算、不被催**，以便我不会因为怕被记录而干脆不用这个工具。
- 作为一个想做好的人，我希望**追求满分是被鼓励的，而不是被收费或被拦**，以便这个工具不站到我的对面。
- 作为使用者，我希望**事后能看到我自己过去的判断准不准**，以便我用证据而不是情绪来决定去不去。

## 7. 页面与交互说明

### 7.0 首次引导（v2.3 新增，v2.4 修正前进方式）

**触发**：仅在**第一次打开应用**时出现（`settings.onboarded === false`）
**重看入口**：设置页最后一项「再看一遍引导」

**核心原则**：**理念要"体验"，不要"讲述"。**
不做文字自动播放，四屏全部由用户主动推进——**点击推进是引导，自动播放是灌输**。

**前进方式**：底部一个明确的按钮（屏 1–3 为「继续」，屏 4 为「开始」），
**点击屏幕其他区域不响应**——原因见 7.0.5。

---

#### 7.0.1 屏 1

```
每天都有很多事想做。
但总有一些，
一直停在"想做"。
```

三行依次淡入，每行间隔 350ms。

---

#### 7.0.2 屏 2（情绪核心）

```
不是因为你懒。

是因为你在等——
等条件再好一点，
等计划再周全一点，
等自己有把握一点。

而那个时刻一直没来。
你只是，一直在准备开始。
```

**节奏要求（不要赶）**：
- 「不是因为你懒。」单独出现，停 400ms
- 三个「等」依次出现，每个间隔 250ms，然后停 600ms
- 最后两行一起出现

**为什么这三句「等」是核心**：它把完美主义者那三种说不出口的说辞具体化了——条件不够完美、计划还不周全、担心做不到 100 分。**触动来自精确，不来自温柔。**

**为什么保留「不是因为你懒」**：它把用户从自责里拉出来，是他愿意继续往下看的前提。没有这一句，后面三屏都读不进去。

---

#### 7.0.3 屏 3（含交互，必须实现）

**文字**：`有没有算过这笔账：`

**精力条**：5 个格子，分三阶段呈现

| 阶段 | 表现 | 停留 |
|---|---|---|
| 1 | 5 格全为浅灰 `#EDEAE2` | — |
| 2 | 第 1 格扩展成占满 5 格宽的墨绿长条，下方标注「一件做到 100 分」 | 1.2s |
| 3 | 过渡为 5 个独立墨绿格，下方标注「五件各 60 分」 | 1.2s |

**交互（不可省）**：
自动播完两态后，出现两个可点击标签 `[ 一件做到 100 分 ]` `[ 五件各 60 分 ]`，用户可反复点击切换。

**为什么必须可点**：这是整个引导唯一需要用户动手的地方。**结论必须由他自己算出来**，产品只负责把账摆在桌上。

**收尾文字**：
```
一件做到 100 分的力气，
够你做五件 60 分的。
```

最后一行出现后 400ms，底部浮出主按钮 `[ 开始 ]`。

#### 7.0.5 跳过与规则

| 规则 | 说明 |
|---|---|
| 「跳过」位置 | 右上角，**屏 1 就可见**，任何一屏可点 |
| 跳过行为 | 立即写入 `onboarded = true`，切首页，**不做二次确认** |
| **前进方式** | **只有点击底部前进按钮才推进**；点击屏幕其他区域**不响应**；**不自动播放** |
| 前进按钮（屏 1–3） | 描边次按钮，44px 高，水平居中，宽度自适应（左右 padding 32px），文案「继续」 |
| 前进按钮（屏 4） | 实心主按钮（`--accent`），文案「开始」；**用形态差异传达"这是最后一步"** |
| 按钮出现时机 | 该屏内容全部出现后 400ms 淡入 |
| 进度指示 | **不显示「1/4」这类文字**（会让人焦虑还有几屏） |
| 回退 | **不提供「上一步」**（四屏很短，回退反而添乱） |
| 重看 | 从屏 1 开始，结束后回**设置页**（不是首页），不修改 `onboarded` |

**⚠️ 为什么放弃「点击任意位置推进」（v2.4 修正）**

屏 3 有两个可点击的切换标签（「一件做到 100 分」/「五件各 60 分」）。如果整屏都响应点击，**用户点标签时会连带触发推进，直接跳屏——那一屏最关键的东西就没体验到了**。

全屏可点只在"这一屏没有任何可点元素"时才安全。屏 3 打破了这个前提，所以必须改成明确按钮。

**代价与接受理由**：从"点哪都行"变成"必须找按钮"，每个屏多一点认知成本。但换来的是**一致性和不误触**——四屏同一个位置同一个按钮，用户第二屏就形成肌肉记忆，实际成本比想象中小。

**不支持滑动手势**：屏 3 的标签会让横向滑动更容易误触，且滑动与产品"克制"的气质不符。

---

#### 7.0.6 明确不做配乐

**四屏全程无音乐、无音效。**

理由：
1. 浏览器禁止自动播放音频，必须等用户交互，会造成音乐与画面错位
2. 产品整个调性建立在"安静"上，配乐会立刻把它变成宣传片
3. 用户可能在地铁、办公室、凌晨打开，突然出声是冒犯

**氛围靠节奏实现，不靠声音**：文字出现间隔、屏间停顿、屏 3 过渡时长，这些"时间上的呼吸"就是氛围。

### 7.1 计划创建（两个入口，两种表单）

**入口**：
- 今日池「+ 添加」→ 创建今日计划
- 想做池「+ 添加」→ 放进想做池

**⚠️ 两个池子的表单必须不同（v2.1 修正）**：

| 池子 | 是否问时间 | 原因 |
|---|---|---|
| 今日池 | **必填** | 拦截需要触发时机 |
| 想做池 | **不问** | 想做池是收纳欲望的地方，**一问时间就变成了压着期限的待办** |

**今日池表单**：

| 字段 | 必填 | 说明 |
|---|---|---|
| 这件事是什么 | 是 | 一句话，硬限 20 字，超长截断 |
| 什么时候做 | 是 | 时间选择器，**仅限今天的具体时刻** |
| 最没阻力的一步 | 否 | 用于降档动作；不填则用任务类型模板 |

**⚠️ 今日池只允许"今天"（v2.2 修正）**：
如果允许选明天，今日池里就会躺着"明天的事"，用户看到的时间轴直接失真。
**明天及以后的事走想做池**，到那天再移过来。

这样模型才干净：
> **今日池 = 今天；想做池 = 今天以外的一切（包括明天）。**

**想做池表单**（只有一个字段）：

| 字段 | 必填 |
|---|---|
| 这件事是什么 | 是 |

标题：`放进想做池`
副文案：`不问时间。想到什么先放着，等它变成「今天要做」的时候再说。`

**从想做池移入今日池**：
必须补时间（因为即将需要触发拦截）。界面只问一件事：
> 「{任务名}」什么时候做？

**为什么今日池时间必填**：拦截依赖明确的时间点。这是试用版最重要的一个假设检验——**如果用户不愿给时间，说明整套机制的前提不成立，这个发现本身就是试用版的产出。**

**注意：这条只适用于今日池。** 想做池不问时间，恰恰是因为它不需要触发。

**辅助文案**（今日池表单，「最没阻力的一步」下方小字）：
> 等你不想动的时候，只要做完这一件就算数。
> 判断标准：这一步能不能被"今天状态不好"这个理由否掉？否不掉，就对了。

**时间字段下方提示**：
> 时间必填。到点才会有人来问你那一句。

### 7.2 拦截卡（核心屏，全产品成败在此）

**触发**：到达计划时间的时刻（误差 ≤ 1 分钟）

**布局（自上而下）**：

```
─────────────────────────────
明早 7:00 · 健身 · 第 4 天

今天你大概会用什么理由不去？

用你自己的话说
┌─────────────────────────┐
│ 一句话就行                │
└─────────────────────────┘
[ 就这段话，继续 ]        ← 仅在输入非空时出现

或者，挑一句最像的
  → 我怕今天做不好
  → 我今天有更要紧的事
  → 我身体确实不舒服
  → 我说不清，就是不想动

─────────────────────────────
      [      我去了      ]        ← 底部固定，视觉权重最高
─────────────────────────────
```

**首次出现时的说明（v2.3 新增）**

用户第一次看到这一屏时，在问句下方显示一行：

> 说实话就行，它不会评价你。

| 规则 | 说明 |
|---|---|
| 样式 | 11.5px，`--ink-3`，**无边框、无底色，不是 tips 气泡** |
| 出现次数 | 只在第一次（`settings.firstInterceptSeen`），第二次起不再出现 |
| 作用 | 它回答的不是"怎么操作"，而是**"这算考核吗"**——这是新人最大的疑虑 |

**为什么不在首页做新手引导**：首页只有三个元素（时间、任务名、满分入口），没有需要教的；而 tips 弹框会挡住「+ 添加」，用户第一次进来最想做的是加一件事，用一个框拦住他的第一个动作得不偿失。

**两条互斥路径（核心规则）**：

| 路径 | 用户动作 | 走向 |
|---|---|---|
| **自己说** | 输入框写一句话 → 点「就这段话，继续」 | 走分支 A（拆解） |
| **挑一句** | 点四个入口之一 | 走对应分支 |

**为什么写了理由之后不再让他分类**：
愿意写下来的人，说明他还在跟自己的理由对话，拆解对他有效；而"有更要紧的事""身体不舒服"这类，用户会直接点选项——**选项的措辞本身就在替他说话**，他不需要再费劲描述一遍。多一次分类，就是多一层摩擦，而这一屏最不能有摩擦。

**⚠️ 但注意：路径合并 ≠ 归属合并。**
写理由的人虽然走 A 路径，但这**条记录的理由归属是他自己的原话，不是标签 A**（详见 7.3）。混为一谈会导致系统给他看"我怕今天做不好"的历史统计，而他从没这么说过。

**⚠️ 认知负担的教训（v1.5 修正，务必保留）**：
v1.4 之前把输入框与四个入口平铺在同一屏、且没有分组标题，用户会产生**三种互斥的解读**：直接选？只写？写完再点选项分类？——**三种都说得通，就是这个设计失败了。**

修法：用两个分组标题「用你自己的话说」/「或者，挑一句最像的」充当说明书，**不再额外增加解释性文字**。

**交互规则**：

| 规则 | 说明 |
|---|---|
| 输入框硬限一行 | 超出一行自动截断，不提示、不警告 |
| 提交按钮仅在输入非空时出现 | 避免"空着点了会发生什么"的疑问 |
| 四个入口由用户自己点 | **产品永不猜测用户属于哪一支** |
| 「我去了」不需前置操作 | 任何时候点都直接成功，不做二次确认 |
| 「我去了」视觉权重最高 | 实心主色、全宽、固定底部；其余全部为次级样式 |
| 无关闭按钮 | 用户可直接退出应用（等同于未响应） |

**设计意图**：问"去不去"，用户是被审问者，本能防守；问"理由是什么"，用户已经站到"要去"那一侧，只是在陈述障碍。

### 7.3 分支 A：我怕今天做不好（拆解页）

**展示顺序（严格固定）**：

1. 用户填写的原话（若有）
2. 证词卡（仅在同一 `reason_key` 第 3/5/8 次时出现，详见下方规则）
3. 校准句
4. 降档动作
5. 行动按钮

**文案**：

> 你在比较「练 60 分的效果」和「练 100 分的效果」。
> 但今天真实的选择是「练 60 分的效果」和「0」。

（证词卡，条件触发）
> 「我怕今天做不好」这个理由，你今年用过 9 次。
> 其中 7 次，你后来觉得其实该去。
> 另外 2 次，你觉得幸好没去。

**⚠️ 路径与归属必须分离（v1.9 修正，核心规则）**

两个概念，**绝不能挤进同一个字段**：

| 概念 | 含义 | 取值 |
|---|---|---|
| `branch` | 走了哪条**处理路径** | A 拆解 / B 放行 / C 放行 / D 不追问 / went 直接去了 |
| `reason_key` | 这条记录的**理由归属**（证词指纹） | `tag:A` 或 归一化后的原话 |

**写自由理由的人：路径是 A，但归属不是 A。**

- `branch = A`（因为要进拆解页）✓
- `reason_key = 归一化原话`（他的理由是那句话）✓
- **绝不允许** `reason_key = tag:A`

**为什么**：用户写"1111111"，如果系统把它归到"我怕今天做不好"，再展示那个标签的历史统计，等于**编造归类**——这和编造原话是同一类错误。

**证词卡的三种情况**：

| 用户入口 | 指纹来源 | 文案措辞 | 触发门槛 |
|---|---|---|---|
| 点了分支标签 | `tag:A` 的累计次数 | 「{标签}」**这个理由** | ≥ 3 次 |
| 写了自由理由 | 该原话**精确重复**的次数（去空格、统一标点；不做语义相似度） | 「{原话}」**这句话** | ≥ 3 次 |
| 两者都不足 3 次 | — | **不展示证词卡**，直接进校准句 | — |

**为什么不展示比硬凑好**：证词的全部力量来自"这确实是你说的"。凑一次假的，整张卡就废了。

> **证词的力量来自真实，不来自煽动。宁可这一次不说，也不能说一句他没说过的话。**

**两种指纹对应的卡片文案**：

只点了标签：
> 「我怕今天做不好」这个理由，你今年用过 9 次。
> 其中 7 次，你后来觉得其实该去。另外 2 次，你觉得幸好没去。

写了自己的原话（且该原话重复 ≥3 次）：
> 「太累了，练了效果不好」这句话，你说过 4 次。
> 其中 3 次，你后来觉得其实该去。

**为什么两种结果都要写出来（v1.7 修正）**：只报"你错了 7 次"是单方面控诉，用户会本能抵触。完整呈现，让他自己得出"这个理由多半站不住"的结论——**自己得出的结论才有效。**

**首次展示证词卡时，附一行来源说明**（透明度放在这里，不放在当晚一问）：
> 这些数字来自你每晚回答的那个问题。随时可以在设置里关掉。

（降档动作）
> 它管不到的事：穿鞋，下楼走一圈

**按钮**：
- 主：[ 就做这个 ]
- 次：[ 今天不做了 ]（文字链，点击后进入放行态的轻量版）

**硬性约束**：
- 校准句**必须使用「60 分」这三个字**，不做抽象化改写——它每次出现都在定义产品名
- 禁止任何打气话术（"你可以的""坚持一下""加油"）
- 禁止解释原理、禁止教学段落
- 校准句必须在降档动作之前，顺序不可调换

### 7.4 分支 B：我今天有更要紧的事（放行）

**文案（仅一句）**：

> 好，记下了。这件事我先放回想做池，它不会跑，你也不用惦记。

**按钮**：[ 知道了 ]

**行为**：计划自动回到想做池，**不设截止、不计算次数、不二次确认**。

**禁止**：
- ❌ 不问"什么时候补上"
- ❌ 不显示"这是本月第 N 次"
- ❌ 不做任何安抚性说教（"没关系下次加油"也是压力）

### 7.5 分支 C：我身体确实不舒服（放行）

**文案**：

> 今天就别去了。这不是借口。

**按钮**：[ 好好休息 ]

**行为**：计划标记为「已放行」，当日不再提醒，不计入任何统计。

**设计意图**：这是产品的伦理底线。必须给得**痛快、完全不带评判**——被试用的用户如果感觉"生病了还要解释"，会立刻卸载。

### 7.6 分支 D：我说不清，就是不想动（不追问）

**文案**：

> 好，那不找了。有时候就是不想动，这不用解释。

接着给降档动作（同 7.3 第 4 步）+ [ 就做这个 ]

**设计意图**：**免除他解释的义务，比逼他承认更有效。** 完美主义者最怕的恰恰是"说不清楚"。

### 7.7 已行动确认（正向反馈）

**触发**：点击「我去了」或「就做这个」之后

**核心原则**：用户刚刚战胜了自己。这一屏说什么，决定他下次还愿不愿意战胜自己。

- **不给夸奖**（"你太棒了""坚持得不错"）。夸奖是最弱的反馈，第三天就免疫
- **不评价质量**（不说做得好不好）
- **不解释产品逻辑**。禁止出现"今晚不会有人来问你"这类内容——那讲的是我们的推送规则，跟用户此刻的感受无关
- **做法：把他的胜利视觉化，而不是用语言夸他**

**布局**：

```
你去了。

我太累了，练了效果不好        ← 他刚写下的理由，加删除线、淡色

今年第 12 次。
把「不去」改成「去了」。
```

**这一屏只做一件事：反馈。不追问、不派任务。**

满分表态已从这一屏移出（见 7.7b）。原因：刚做完事的人被问"想做到几分"，本质上还是在给他派任务；而做完之后自己回计划页点一下"做到满分了"，那是他自己的判断——**前者是考核，后者是自由**。

**为什么核心是「划掉借口」**：
那条删除线不是产品划的，是**他自己用行动划的**。借口还写在那里，只是失效了。这个画面比任何一句夸奖都有力，而且它完全不是评价——只是把事实摆出来。

**累积计数的规则**：
- 文案：`今年第 {N} 次。把「不去」改成「去了」。`
- 计数口径：当日有拦截记录（写了理由或选了分支）且最终 `action_taken = true`
- **只在用户写过理由时展示**（此时才有"推翻"这个动作）；直接点「我去了」且无理由的，不展示计数
- **不做连续天数、不做中断归零、不做勋章**。这是账本，不是奖章

**硬性约束**：
- **路径终点**：该屏之后直接结束，**不进入当晚一问**
- **不出现任何时间问句、代价提示、条件从句**（不能用"但是""不过""记得"开头）
- 满分表态**不出现在这一屏**（见 7.7b）。若用户在计划创建阶段或拦截卡上表达"我想做到满分"，产品不做任何拦截，也不追问交付时间
- 该屏停留 ≤ 3 秒即可退出，不做强制

### 7.7b 满分标记（今日计划页，主动认领）

**位置**：今日池中**每个计划行**的右侧，统一一个轻量入口：`满分`
（已标记时显示 `100`，为静态文本，不可再点）

**为什么每个计划都有，而不是只在"已完成"的行上**：
本产品**不设独立的"完成"按钮**。标记满分即为完成；不标记则什么都不发生，不催、不统计、不显示逾期。这样避免了"任务管理"那一套状态机，也避免用户为了点一个"完成"而产生额外负担。

**⚠️ 产品不审核这个标记。** 用户可以在未行动时就点满分，产品不拦、不质疑、不提示。**它不是绩效记录，是一次自我承认。**

**交互**：
1. 用户点击「满分」
2. 展示正向反馈
3. 该计划显示为 `100`

**反馈文案**：

> 100 分。
> 这次你做得很好。

**为什么这样写（v1.6 修正）**：
- 两句，**没有任何转折、任何补充、任何"但是"**。任何补充都是给成就打折
- 原稿「你本来可以只交 60 分的」**已废弃**。它本意是肯定超额付出，实际效果是把 60 分设成了参照系——等于告诉一个做到 100 分的人"其实 60 分也够"，听感是降格
- 原则依据：**60 分是底线，不是目标**（见 1.5 ④）

**设计原则**：
- **由用户主动认领，产品永不询问**。问"想做到几分"是考核，让他自己标是自由
- 不做"未标记 = 只做到 60 分"的对比展示，不统计满分率，不做排行
- 满分标记**不参与任何指标计算**（北极星是"被推翻的借口数"，与此无关）

**禁止**：
- 禁止「你真棒」「了不起」等夸奖
- 禁止任何形式的"下次也要这样"
- 禁止把满分标记做成徽章、等级、连击

### 7.8 当晚一问（事后证词采集）

**触发**：当日 21:00，**且同时满足**：
1. 该计划当日最终未行动（`action_taken = false`）
2. 该计划走的分支是 **A（我怕今天做不好）或 D（我说不清）**

**⚠️ 两类计划永远不复盘（v1.7 修正，重要）**：

| 分支 | 是否复盘 | 原因 |
|---|---|---|
| A 我怕今天做不好（最终没去） | ✅ 问 | 这个决定值得检验 |
| D 我说不清，就是不想动（没去） | ✅ 问 | 同上 |
| **B 我今天有更要紧的事** | ❌ **不问** | 那是用户的优先级判断，产品无权质疑 |
| **C 我身体确实不舒服** | ❌ **不问** | 产品已经说过"这不是借口"，再问就是背弃承诺 |

**核心边界**：
> **证词只用来检验"被完美主义留下的决定"，不用来检验"合理的放行"。**

两条推导：

1. **已经行动的计划，也不问。** 行动本身已经回答了这个问题；再推一条问"那个决定你怎么看"，是无用途的打扰
2. **产品已经放行的事，不问。** 分支 C 那一屏的文案是「今天就别去了。这不是借口。」——既然产品已经判定"这不是需要检验的决定"，晚上再回来问"庆幸没去还是有点后悔"，用户会一个选项都不想选。**这不是选项不够，是不该问。**

这条边界定义了产品的行为气质：**它只在"可能被借口留下的那一类决定"上出现；合理的放行和已经完成的事，它都该彻底消失。**

**普通未响应（既没写理由也没选分支就退出）**：不做当晚一问。

**文案**：

```
早上那个决定，现在你怎么看？

  → 幸好没去
  → 其实该去的
  → 说不好

        这次不说了
```

**选项设计说明**：
- **「有点后悔」→「其实该去的」**：'后悔'是情绪，承认它等于承认自己蠢，人会本能回避；'该去的'是复盘判断，更像理性结论，容易承认
- **「想不起来了」→「说不好」**：更真实。多数情况不是忘了，是判断不了
- 三个选项**都不带自我批判**

**「这次不说了」出口（必须有，不可省略）**：
- **不回答本身也是一种回答**；强制回答会让他下次不想打开这个应用
- 点跳过后不记录、不补发、不做任何后续提及

**已删除的内容（v1.7）**：
原版底部有一行「这一次回答会存下来。下次你说「我怕今天做不好」的时候，它可能会被拿出来。」——两个问题：

1. 用户若是从分支 C 进来，这行字在**用一个他没用过的理由提示他**
2. 更严重：**它把"记录"变成了"取证"**——还没回答就预告"这会被拿出来"，是威胁感

**透明度不该省，但要挪到该说的时刻**：在第一次亮出证词卡时告知记录来源（见 7.3）。

**规则**：
- 一次点击即完成，无后续追问
- 未响应不补发、不记录为失败
- 可在设置中整体关闭（默认开启）

### 7.9 想做池 / 今日池（v1.2：取消硬上限）

| 池子 | 上限 | 行为 |
|---|---|---|
| 今日池 | **无上限，完全由用户决定** | 超过参考容量时，仅做一次可见提示，不阻断 |
| 想做池 | 无上限 | 收纳欲望，不排序、不提醒、不计逾期 |

**⚠️ 定义变更（务必注意，避免后续误解）**：
v1.1 之前，今日池通过容量上限承担「隔绝欲望」的职能。v1.2 取消上限后，**两个池子的区别退化为纯粹的时间归属**（今天做 / 以后做），不再承担欲望隔离机制。
欲望隔离改为由「容量可视化 + 参考值对比」承担，属于**提示性**而非**约束性**机制。这是有意为之的取舍：**宁可少一层约束，也不让产品替用户决定一天能做几件事。**

#### 7.9.1 参考容量（Reference Capacity）

**定义**：参考容量 `R` 不是限制，只用于对比。取值优先级：
1. 用户近 7 日「实际完成件数」的中位数（有 ≥3 天数据时）
2. 首次引导时用户自填的一个数（无历史数据时）
3. 首次引导可跳过，跳过则不做超载提示

**首次引导文案**（只问一次，可跳过）：
> 你一天大概能认真做完几件？
>
> 　[ 1 ]　[ 2 ]　[ 3 ]　[ 4 ]　[ 5 ]　[ 6 ]
>
> 这不是上限，只用来和实际做个对照。随时能改。

#### 7.9.2 超载时的唯一提示（每日至多一次）

当今日池件数超过 `R` 时，在今日池顶部出现一行字，样式为中性浅色（**不使用警告色、不使用图标、不弹窗、不阻断**）：

> 今天第 7 件。你最近一周实际做完的是 3.2 件。

**规则**：
- 每日最多出现一次，关闭后当日不再出现
- 不阻止任何操作，加入按钮行为完全不变
- 不回忆、不累计、不在次日重复提醒
- **禁止**出现"太多了""建议删掉""你做得完吗"等评价性表达

**设计意图**：不是产品告诉用户"太多了"，而是**把他自己的数字摆出来让他自己判断**。物理事实比标语有力——标语第三天就会隐形（横幅盲视），数字不会。

#### 7.9.3 「欲望越多焦虑越多」这句话放在哪

**日常界面一句都不放。** 常驻标语会从提醒退化为教训，与"绝不施压"原则冲突。

该句只出现在两个"用户愿意停下来听"的时机，且各只出现一次：

| 位置 | 文案 |
|---|---|
| **首次引导最后一屏** | 欲望越多，焦虑越多。人的精力是有限的——写下来的时候多问一句：今天真的做得完吗？ |
| **月度回顾页顶部** | 你这个月平均每天写下 5.2 件，实际做完 3.1 件。 |

**为什么**：道理要在用户愿意听的时候讲。

#### 7.9.4 通用规则

- 想做池中的事项**永不显示"逾期""已搁置 N 天"**
- 从想做池移入今日池时，必须重新指定时间
- 参考容量 `R` **可以在任何时候修改，立即生效，无任何确认弹窗**（因为它不承担约束职能，无需延迟）
- 参考容量变更历史不追踪、不呈现——它已经不再是一个需要被审视的指标

### 7.9.5 计划行的统一结构（v2.0）

每个计划行**只有三个元素**：**时间 · 任务名 · 满分入口**。

| 元素 | 说明 |
|---|---|
| 时间 | 计划时刻 |
| 任务名 | 一句话 |
| 满分入口 | 未标记 → `满分`（轻量文字按钮）；已标记 → `100`（静态） |

**❌ 严禁出现的状态标签**：

| 禁止标签 | 为什么禁止 |
|---|---|
| 「卡了三天」「已逾期」「逾期 N 天」 | **违反原则 ②「绝不施压」**。逾期提示就是审判 |
| 「第 4 天」「连续 N 天」 | 违反"不做连续天数、不做勋章"的决定 |
| 「刚加的」「新」 | 无信息量，制造视觉噪音 |

**为什么这一条必须写死在 PRD 里**：
原型里曾经出现过「卡了三天」「第 4 天」这类标签，它们不只是"显得乱"——**直接违反产品原则**。原型是给开发看的，开发会照着做，**原型里的违规元素最终会变成产品里的违规功能**。

---

### 7.9.6 今日池排序规则（v2.2）

- **严格按时间升序**，新增计划自动插入正确位置（不是追加到末尾）
- **已标记满分的项不挪动位置**

**为什么已完成项不挪到底部**：
1. 时间轴是客观的，不该因为"做完了"而变形
2. 产品要的是**"这一天的形状"**，不是待办清零的爽感
3. 产品本身有事后回看的诉求（证词），历史留在原位才看得见

**视觉区分靠 `100` 标记，不靠位置。**

---

### 7.10 暂不实现的设计观察

**步骤 vs 事项**：当前以"件"为计数单位。但把一个大任务拆成六个步骤的人，会被算成 6 件——上限（即便只是提示）拦住的往往是写得认真的人，而不是真正超载的人。

**暂不实现**，因为会增加结构复杂度。若试用期数据显示"用户普遍把一件事拆得很细"，下一版应将计数单位从「件」改为「事」（步骤不计入）。

## 9. 需求条目（EARS）

### Ubiquitous（系统始终满足）

- U1. 系统应始终不展示任何针对任务完成质量的分数、评级、完成度百分比或排行榜。
- U2. 系统应在所有文案中不使用催促性表达（含"逾期""已拖延""你还没""加油""坚持"）。
- U3. 系统应保证「我去了」按钮在任何拦截状态下均可见且可点击。
- U4. 系统应始终将校准句中的「60 分」作为固定表达，不做同义替换。

### Event-driven（事件触发）

- E1. 当到达用户设定的计划时间时，系统应推送拦截卡。
- E2. 当用户点击「我去了」时，系统应记录一次行动并展示正向反馈屏（含划掉的理由与累计次数），且**不展示任何满分询问或后续追问**。
- E3. 当用户提交自己输入的理由时，系统应直接进入分支 A（拆解），且**不要求用户再做分支分类**。
- E4. 当用户选择「我今天有更要紧的事」时，系统应展示放行文案，并将计划移回想做池。- E5. 当用户选择「我身体确实不舒服」时，系统应展示放行文案，并将计划标记为当日已放行。
- E6. 当用户选择「我说不清，就是不想动」时，系统应展示免除解释文案，并直接展示降档动作。
- E7. 当用户点击「就做这个」时，系统应记录一次行动并展示正向反馈屏。
- E7a. 当用户点击今日池某已完成事项的「做到满分了」时，系统应展示满分反馈，且不做任何后续追问。
- E8. 当同一 `reason_key` 累计达到第 3、5、8 次时，系统应在校准句之前展示证词卡。
- E8a. 若用户输入的自由理由历史精确重复次数不足 3 次，则系统不应展示该理由的证词卡。
- E8b. 系统不应将用户输入的自由理由归入任何分支标签的理由指纹。
- E9. 当当日 21:00 到达时，系统应对当日「分支为 A 或 D 且最终未行动」的计划触发事后一问。
- E9a. 若计划当日最终已行动（含点击「我去了」「就做这个」或进入正向反馈屏），则系统不应对其触发事后一问。
- E9b. 系统不应为分支 B（有更要紧的事）、分支 C（身体不舒服）的计划触发事后一问。
- E9c. 当用户在当晚一问中点击「这次不说了」时，系统应结束该次询问，且不记录任何结果、不做任何后续提及。
- E11. 系统应在今日池与想做池分别提供添加入口。
- E12. 当用户在今日池添加计划时，系统应要求填写时间，未填写时不可提交。
- E13. 当用户在想做池添加计划时，系统不应询问时间。
- E14. 当用户将想做池的计划移入今日池时，系统应要求补充时间后方可完成移动。
- E15. 当应用首次启动且 `settings.onboarded === false` 时，系统应进入首次引导并展示第一屏。
- E15a. 系统应仅在用户点击底部前进按钮时切换到下一屏；点击屏幕其他区域不得触发推进。
- E16. 当用户在引导中点击「跳过」时，系统应立即写入 `onboarded = true` 并进入首页，且不做二次确认。
- E17. 当引导播至屏 3 并完成两态自动过渡后，系统应提供两个可点击标签，允许用户在两态之间反复切换。
- E18. 当用户首次看到拦截卡时，系统应在主问句下方展示一次说明「说实话就行，它不会评价你。」，此后再不展示。

### Unwanted（异常与边界）

- UW1. 若推送权限未开启，则系统应在应用内以横幅提示一次，且不再重复请求。
- UW2. 若用户未在拦截卡上做出任何选择即退出，则系统应记录为「未响应」，不计为失败、不发送二次催促。
- UW3. 若用户对当晚一问未响应，则系统不应补发、不应计入任何统计。
- UW4. 若「最没阻力的一步」未预写且无匹配的任务类型模板，则系统应展示一条通用降档动作，不阻断流程。
- UW5. 若用户输入的降档动作超过一行，则系统应截断展示且不弹出警告。
- UW6. 若同一计划在当日重复到达提醒时间（用户修改过时间），则系统应只对最新时间触发一次拦截。
- UW7. 若用户无历史数据且跳过了首次引导，则系统不应展示任何超载提示。
- UW8. 若超载提示当日已被关闭，则系统不应以任何其他形式（角标、颜色、文案）重复表达同一信息。

### State-driven（状态相关）

- S1. 系统不应为今日池设置任何硬性数量上限，加入按钮在任何件数下均保持可用。
- S1a. 当今日池件数超过参考容量 R 时，系统应展示一次超载提示，且该提示不应阻断任何操作。
- S1b. 同一自然日内，超载提示最多出现一次，关闭后当日不再出现。
- S1c. 参考容量 R 在用户修改后应立即生效，且不应产生确认弹窗或生效延迟。
- S1d. 系统不应在任何日常界面常驻展示"欲望越多焦虑越多"类理念文案；该类文案仅可在首次引导与月度回顾中出现，且各限一次。
- S2. 当计划处于想做池状态时，系统应不展示任何逾期、搁置时长、次数信息。
- S3. 当计划已被分支 C 放行时，系统应在当日不再对该计划触发拦截。
- S4. 当用户已在设置中关闭事后证词时，系统应不触发 E9。

### Optional（可选功能）

- O1. 若用户在设置中开启事后证词，系统应执行 E9。
- O2. 若用户为计划预写了「最没阻力的一步」，系统应在分支 A/D 中优先展示该句，而非模板。
- O3. 若用户点击「做到满分了」，系统应展示满分反馈，且不附加任何后续条件、不做追问、不计入任何比率指标。

## 10. 验收标准

### 10.1 核心链路

**首次引导**
- [ ] 首次打开进入引导，第二次起不再出现
- [ ] 只有点击底部前进按钮才推进；**点击屏幕其他区域不触发推进**
- [ ] **屏 3 点击两个切换标签时不会连带推进到下一屏**
- [ ] 「跳过」在屏 1 就可见，点击直接进首页，无二次确认
- [ ] 屏 3 自动过渡两态后，两个标签可反复点击切换，动画不卡顿
- [ ] 屏 4「开始」→ 直接进首页
- [ ] 设置页「再看一遍引导」可重放，结束后回设置页
- [ ] 全程无音乐、无音效

**主链路**
- [ ] 创建带时间的计划后，到点准时推送拦截卡（误差 ≤ 1 分钟）
- [ ] 拦截卡上「我去了」无需任何前置操作即可点击成功
- [ ] 输入框留空时，四个归类入口均可正常走完流程
- [ ] 选择分支 A 后，页面依次展示：证词卡（若触发）→ 校准句 → 降档动作 → 按钮
- [ ] 选择分支 A 后必须能看到「60 分」这三个字且未被替换
- [ ] 用户未写理由时，证词卡表述为「{分支标签}」这个理由，**不出现任何"你说过的话"**
- [ ] 用户写过理由时，**不展示任何分支标签的证词卡**；该原话重复不足 3 次时也不展示证词卡
- [ ] 写自由理由的记录，`reason_key` 为归一化原话，**不等于 tag:A**
- [ ] 选择「就做这个」后，记录为一次行动，且进入正向反馈屏
- [ ] 已行动的计划**不进入**当晚一问；分支 A / D 且未行动的计划正常进入
- [ ] 分支 B（有更要紧的事）、分支 C（身体不舒服）的计划**不进入**当晚一问
- [ ] 当晚一问提供「这次不说了」出口，点击后无任何记录与后续
- [ ] 已行动后，界面不出现任何"今晚不会有人来问你"类产品逻辑说明，且无任何追问入口
- [ ] 已行动页**不出现**任何"想做到几分"类询问
- [ ] 写过理由并行动时，该理由以删除线形式展示，并展示「今年第 N 次」累积
- [ ] 无理由直接点「我去了」时，不展示累积计数
- [ ] 拦截卡上「用你自己的话说」与「或者，挑一句最像的」两个分组标题同时存在，视觉分组清晰
- [ ] 输入框为空时不显示提交按钮；写了理由提交后直接进入拆解，不再要求分类
- [ ] 今日池与想做池各有添加入口，且表单不同
- [ ] 新增的计划按时间自动插入正确位置，不追加到末尾
- [ ] 已标记满分的项在列表中的位置不因标记而改变
- [ ] 今日池添加时不填时间无法提交；想做池添加时不出现时间字段
- [ ] 从想做池点「今天做」会先要求补时间，确认后才进入今日池
- [ ] 今日池每个计划行都有满分入口，已标记的显示 `100` 且不可再点
- [ ] 计划行不出现任何逾期、连续天数、状态标签
- [ ] 选择分支 B 后，计划回到想做池，且该页面只有一句文案 + 一个按钮
- [ ] 选择分支 C 后，当日不再提醒该计划
- [ ] 选择分支 D 后，文案为「好，那不找了…这不用解释」，且紧接降档动作

### 10.2 价值观红线（任一不通过即不可上线）

- [ ] 全流程无任何质量评分、完成度、评级
- [ ] 全流程无催促性文案
- [ ] 分支 B/C 无任何"什么时候补上""本月第 N 次""下次加油"类内容
- [ ] 满分反馈不含时间问句、代价提示、转折词、夸奖
- [ ] 想做池中不显示逾期与搁置天数

### 10.3 异常

- [ ] 关闭推送权限后，应用内提示一次，无重复弹窗
- [ ] 拦截卡不做任何选择直接退出，不产生催促、不计失败
- [ ] 今日池不设任何数量上限；加入第 10 件时按钮行为与第 1 件完全一致
- [ ] 超过参考容量时出现一行超载提示，且不阻断任何操作
- [ ] 同一自然日内，超载提示最多出现一次，关闭后当日不再出现
- [ ] 参考容量修改后立即生效，无确认弹窗
- [ ] 日常界面不存在任何常驻理念标语（"欲望越多焦虑越多"仅出现在首次引导与月度回顾）

## 11. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| **拦截本身成为新阻力** | 用户三天内关通知，产品死亡 | 主按钮永远最高权重；分支 B/C 只需一次点击；不做二次确认 |
| **用户不打字** | 证词失去原话素材 | 允许留空；用归类标签作为理由指纹兜底 |
| **计划无时间点** | 整套拦截没有触发时机 | 时间设为必填；若用户抗拒，即为关键产品发现，需回到机制层重新设计触发 |
| **证词显得唠叨** | 用户反感、关闭功能 | 严格限第 3/5/8 次；只陈述次数，禁止评价 |
| **60 分被误解为偷懒许可** | 价值观被质疑 | 校准句固定保留"60 分"；降档动作永远配行动入口，不单独出现 |
| **身体信号被滥用** | 分支 C 成为万能出口 | 试用版不做限制（限制即施压）；观察占比，超过 30% 再议 |
| **取消上限后超载提示被无视** | 用户仍写下 8 件做不完，机制退化为纯记录 | 提示只用他自己的历史数据、每日仅一次；观察"超载后是否移除件数"，若连续一周为 0，说明提示无效，需回到约束设计 |
