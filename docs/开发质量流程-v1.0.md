# 开发质量流程 v1.0

> **原则：质量流程服务开发速度，不是反过来。**
> 一个让开发变慢的流程，最后一定会被绕过。

---

## 0. 一句话总览

```
写代码
  ↓
本地自检（构建 + 测试 + 自己点一遍）
  ↓
开 PR
  ↓
CI 自动跑（lint / typecheck / test / build / 文案红线）
  ↓
AI 代码审查（带上下文包）→ 三段处理：发现 → 筛选 → 处理
  ↓
人工判断（只有人能做的那部分）
  ↓
合并队列（GitHub 原生功能，每次合并前重跑 CI）
  ↓
合入 main
  ↓
问题记入 PROBLEMS.md
```

---

## 1. 分层：什么做，什么不做

| 层 | 内容 | 成本 | 做不做 |
|---|---|---|---|
| **必做** | 分支保护 + CI 四件套 + 六条业务规则测试 + 文案红线扫描 + 问题台账 | 1 小时配置 | ✅ |
| **值得做** | Playwright 冒烟三条 + AI 审查带上下文包 + `npm audit` | 半天 | ✅ 按需启用 |
| **不做** | 自建合并队列、覆盖率门禁、重型 SAST、独立安全审核岗、多 agent 流水线 | — | ❌ |

### 为什么不做自建合并队列

原方案是「每个 PR 合并后重跑全量测试，下一个 PR 基于新主干再跑」。这在数学上是 O(n²)——第 N 个 PR 要跑 N 次。

它的目标是对的（保证主分支永远可运行），但 GitHub 有两个现成开关可以达成同样效果：

- **Require branches to be up to date before merging** —— PR 必须基于最新主干才能合
- **Merge Queue** —— 多个 PR 就绪时自动串行验证

**用现成开关，效果一致，省两天。**

## 2. 本地自检（开 PR 之前）

PR 之前必须自己跑一遍，不要交给 CI 发现低级问题。

```bash
cd app
npm run lint          # 规范
npx tsc --noEmit      # 类型
npx vitest run        # 六条业务规则
npm run build         # 能构建
npm run dev           # 起服务，手动点一遍改动的路径
```

**最后一条最重要**：`npm run dev` 起来之后，把改动的那条路径真实点一遍。CI 能证明"跑得通"，证明不了"用起来对"。

## 3. CI（自动跑的部分）

配置文件：`.github/workflows/ci.yml`

### 3.1 主 job：lint / typecheck / test / build

五步串行，任一失败即红。

**`app/package.json` 需要有这几个 script**：

```json
{
  "scripts": {
    "dev": "vite",
    "build": "tsc -b && vite build",
    "lint": "eslint . --max-warnings 0",
    "preview": "vite preview"
  }
}
```

### 3.2 文案红线 job（这个项目独有）

用 `grep` 扫源码中的违规文案，**不依赖 app 是否初始化，任何时候都能跑**：

| 扫描项 | 拦的是什么 |
|---|---|
| `逾期｜已拖延｜连续 N 天｜你还没｜加油｜坚持一下｜你可以的` | 违反原则②「绝不施压」 |
| `完成度｜质量评分｜评级｜排行榜｜得分` | 违反原则③「可数资源，不可数质量」 |

**为什么用 grep 而不是 lint 插件**：这些是产品原则，不是代码规范。用 grep 写在 CI 里，任何人（包括未来的你）一改就能看见规则在哪，比藏在 ESLint 配置里更透明。

### 3.3 六条业务规则的测试（第一版唯一的测试重点）

不做覆盖率门禁，只测这六个地方——它们错了不会报错，只会让数据悄悄变错：

| # | 规则 | 测试要断言什么 |
|---|---|---|
| 1 | `branch` 与 `reasonKey` 分离 | 写自由理由的记录，`reasonKey` 不等于 `tag:A` |
| 2 | 当晚一问触发条件 | 分支 B/C 不进入候选；已行动不进入；未响应不进入 |
| 3 | 证词卡门槛 | 只在第 3/5/8 次展示；`glad = 0` 时不显示"另外 0 次" |
| 4 | 理由归一化 | `"太累了。"` 与 `"太累了"` 归一化后相同 |
| 5 | 列表排序 | 插入后严格升序；标记满分不重排 |
| 6 | 超载提示 | 同一天只出现一次 |

## 4. AI 代码审查（三段式）

### 4.1 发现

把 `.github/AI-REVIEW-CONTEXT.md` 的全文 + 代码 diff 一起发给审查用的 AI。

**这个上下文包不是可选项。** 不带它，AI 会给出一堆与本项目冲突的"最佳实践"建议（加二次确认、加 toast、加设置项、优化文案措辞），筛选成本会超过收益。

### 4.2 筛选（最关键的一步）

AI 会误报，不要全信。筛选只用一个标准：

> **这条问题能不能说清违反了哪一条具体规则？**
>
> 说得清 → 进入待处理
> 说不清（只是"感觉不太好"）→ 忽略

| 等级 | 判定 | 处理 |
|---|---|---|
| **阻断** | 违反四条原则 / 六条业务规则之一，或类型逃逸 | 必须修才能合 |
| **建议** | 有具体理由但不违反硬规则 | 记入台账，决定做不做 |
| **忽略** | 属于上下文包里的禁止建议 | 直接丢掉，不讨论 |

**筛选时的心态**：审查的目的是让代码对，不是让代码多。**一份只有一条阻断问题的报告，比一份二十条的更有价值。**

### 4.3 处理

| 类型 | 动作 |
|---|---|
| 阻断 | 当轮修完，重跑 CI |
| 建议 | 记入 `PROBLEMS.md`，标注优先级。**不阻断合并** |
| 被忽略的误报 | 如果某类误报反复出现，把它加进上下文包的禁止清单 |

**第 3 条是流程自我进化的关键**：误报不是噪音，是上下文包还不够准的信号。

### 4.4 关于"安全审核"

本产品是纯前端 + 本地存储，安全面很窄：

| 真实风险 | 检查方式 |
|---|---|
| 依赖漏洞 | `npm audit`（CI 里跑）+ Dependabot 自动升级 PR |
| XSS | 不渲染用户输入的 HTML（只用 `textContent`），review 时看这一点 |
| 数据泄露 | 本来就没有后端，数据不出设备 |

**不需要**专门上一套 SAST 工具。`npm audit` + review 时看一眼 XSS 就够了。

## 5. 合并策略

### 5.1 分支保护设置（GitHub 网页操作，一次性）

`Settings → Branches → Add branch protection rule`

- Branch name pattern：`main`
- ✅ **Require a pull request before merging**
- ✅ **Require status checks to pass before merging**
  - ✅ **Require branches to be up to date before merging** ← 关键，这就是"每次合并前重跑"
  - 勾选 CI 的两个 check：`lint / typecheck / test / build` 和 `文案与原则红线`
- ✅ **Require conversation resolution before merging**
- ❌ 不要勾 Require approvals（单人项目）

### 5.2 Merge Queue（可选，多 PR 同时就绪时启用）

`Settings → General → Merge queue → Enable`

配置基线：`main`。

**什么时候才需要开它**：真的出现两个以上 PR 同时待合并。单人串行开发用不上，别提前开。

开了之后的行为，正是你原方案想要的效果：

```
PR-1 进入队列 → 基于最新 main 跑一遍 CI → 通过 → 合入 main
PR-2 进入队列 → 基于新的 main 再跑一遍 CI → 通过 → 合入 main
...
```

**这就是"每次轮到它合并时重跑测试"**，但由 GitHub 实现，不需要你写一行代码。

## 6. 问题台账

文件：`PROBLEMS.md`

**每个问题必须记，包括被忽略的误报。**

每条记录三个必填项：

1. **问题现象**（不写"修了某处"，写现象——现象才能被复现和测试）
2. **根因分类**（见台账里的分类表）
3. **能否被自动拦住**

**第三条决定防护方向**：

- 能 → 立刻补一条测试或 lint 规则（不是"以后再说"）
- 不能 → 说明这类问题只能靠人，要写进 PR 清单或 AI 上下文包

**每月看一次**：如果某一类根因反复出现，说明它不是代码问题，是思维方式问题。

## 7. 我能提供的验证能力

你问过这个，这里是准确清单：

| 能力 | 说明 |
|---|---|
| ✅ 编译验证 | `tsc --noEmit` + `vite build` |
| ✅ 单元测试 | `vitest run`，六条业务规则可完整验证 |
| ✅ 起服务 | 后台跑 dev server，验证 HTTP 与渲染内容 |
| ✅ 端到端点击 | 装 Playwright 后可真实点击、断言文本、走完整流程 |
| ✅ 看界面 | 截图后我能直接看，判断布局与配色是否符 UI 规范 |
| ⚠️ 有限 | 能看静态画面，判断不了动效流畅度 |
| ❌ 不能 | 真实手感、文案的心理效果、真机表现（尤其 iOS Safari） |

**结论**：自动化验证我可以兜住，"这个产品到底有没有用"只能靠你和试用者。

## 8. 一次性配置清单

| # | 事项 | 方式 | 耗时 |
|---|---|---|---|
| 1 | 建 GitHub 仓库（根目录 = `60分执行力项目/`） | 网页或 `gh repo create` | 2 分钟 |
| 2 | 推代码 | `git init && git add -A && git commit && git push` | 2 分钟 |
| 3 | 建 `main` 分支保护 | 网页设置，见 5.1 | 5 分钟 |
| 4 | 建 Cloudflare Pages 项目，连仓库 | 网页，构建目录填 `app/dist` | 5 分钟 |
| 5 | 加 `app/package.json` 的 lint / build 脚本 | 脚手架自带，补 lint 即可 | 2 分钟 |
| 6 | 写六条业务规则的单测 | 跟着 `logic/` 三个文件写 | 1 小时（含在开发里） |
| 7 | 开 Dependabot | 仓库 Settings → Code security | 1 分钟 |

**总共约 1 小时**，其中 1 小时那条本来就在开发计划里。

## 9. 每个 PR 的额外时间成本

| 环节 | 时间 |
|---|---|
| 本地自检 | 5 分钟 |
| CI 等待 | 2 分钟（自动） |
| 跑一次 AI 审查 | 3 分钟 |
| 筛选 AI 报告 | 5 分钟 |
| 处理阻断问题 | 视情况 |

**每个 PR 约 15 分钟。** 一天开两个 PR 就是半小时——这个比例是合理的，不会拖垮开发。

**如果某天你觉得这套流程太慢**，那说明该砍的是流程里的某一环（通常是 AI 审查），不是砍掉全部。**分支保护和 CI 那两样不能砍，它们是最便宜的部分。**
